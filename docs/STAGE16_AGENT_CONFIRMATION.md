# 阶段 16：Agent 行动的预览、确认与完成

## 为什么要加确认层

阶段 15 的 `create_learning_plan` 已经能根据画像和 SM-2 队列生成计划。阶段 16 不再让写工具直接进入执行状态，而是把行动拆成三个明确状态：

```text
Agent 生成计划 -> draft
用户确认计划 -> active
用户逐项完成 -> completed
```

这样 Agent 可以提出行动，但最终的业务状态变化由用户确认；这比让模型直接修改画像、复习项或任务状态更容易解释、测试和回滚。

## 后端设计

- `learning_plans.status` 使用 `draft`、`active`、`completed`；
- `POST /api/agent/plans/{plan_id}/confirm` 只允许当前用户确认自己的计划，重复确认是幂等操作；
- `POST /api/agent/plans/{plan_id}/items/{item_id}/complete` 只允许确认后的计划项完成；重复完成同一个计划项不会重复写入；
- 所有计划和计划项查询继续通过 `user_id` 隔离；
- 计划项全部完成后，后端自动把计划状态转为 `completed`；
- 完成计划项暂时不会自动改写画像或 SM-2，避免把“用户点击完成”误当成“能力已经掌握”。

## 前端交互

个人 Agent 页面在收到计划草稿后展示：

1. 草稿状态和计划内容；
2. “确认并开始执行计划”按钮；
3. active 状态下每个计划项的“标记完成”按钮；
4. 所有项目完成后的 completed 状态。

## 面试追问卡

### 为什么完成计划项不直接提高掌握度？

完成是行为信号，不等于知识掌握。掌握度应该来自专项回答、复盘评分和 SM-2 反馈；后续可以把完成记录作为画像的行为信号之一，但不能直接当成得分。

### 如何保证重复点击不会产生重复效果？

确认接口只把 draft 转为 active，已经 active 或 completed 的计划重复调用不会再次写入业务变化。完成接口根据 `item_id` 更新同一个 JSON 计划项，已完成项再次调用仍返回同一计划状态。

### 为什么没有让 LLM 直接决定 status？

status 是业务状态，不是自然语言内容。LLM 只负责理解请求和选择工具，状态转换由后端白名单路由和 Store 方法控制，避免模型输出一个 `completed` 就绕过用户操作。
