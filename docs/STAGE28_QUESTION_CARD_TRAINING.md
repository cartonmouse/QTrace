# Stage28：追问卡驱动专项训练

## 目标

Stage27 已经能从结构化简历项目生成五类追问，并为追问绑定个人文档证据，但卡片停留在“看问题、做准备”。本阶段把它接入真实训练入口：用户从一张卡点击进入专项训练，系统继续读取领域知识、JD 学习计划、长期画像和 SM-2 到期复习，并把本次训练的来源保存下来。

## 完整链路

```text
结构化简历项目
  -> 生成项目追问卡
  -> 用户点击“进入专项训练”
  -> /topic-drill?focus=...&question_card_id=...
  -> 用户选择训练领域
  -> POST /api/interview/start
  -> 校验当前用户的追问卡
  -> 合并卡片焦点 + 显式 focus + 学习计划焦点
  -> 出题器读取领域知识、画像、SM-2 到期项和近期训练
  -> InterviewEngine 创建专项训练会话
  -> 保存 question_card_* 来源字段
  -> 面试页、复盘页、历史记录展示来源
```

前端的卡片只需要携带 `question_card_id`。后端根据当前用户的结构化简历重新解析卡片，自己补齐项目名和简历版本，避免客户端伪造另一位用户的项目证据。

## 三类焦点如何合并

专项出题器原来已经接收 `requested_focus`、画像、领域画像、近期训练和 `due_reviews`。本阶段没有另起一套题库，而是把新的入口接到同一个 seam：

- 追问卡焦点：来自卡片的固定问题，例如“这个项目要解决什么问题？”；
- JD 学习计划焦点：来自已确认的 Agent 计划项，例如“补充 RAG 的离线评估指标”；
- SM-2 队列：由 `review_items.next_review` 判断是否到期，作为出题器的独立优先队列。

如果多个焦点同时存在，后端会将它们组合成一个有来源标签的 `requested_focus`，再交给 Stub 或真实 LLM 出题器。这样“卡片关注项目表达”“JD 关注岗位能力”“SM-2 关注遗忘点”分别保留语义，不会互相覆盖。

重要边界：追问卡和学习计划只提供训练目标，不直接修改画像或 SM-2。只有训练结束并生成复盘后，现有画像写回逻辑才会更新掌握度和复习项；学习计划仍需用户显式确认完成。

## 会话审计字段

`sessions` 新增三个可空字段：

- `question_card_id`：当前简历版本中的追问卡 ID；
- `question_card_project`：后端验证后写入的项目名；
- `question_card_resume_version`：创建训练时卡片使用的简历版本。

旧数据库通过启动迁移补齐这三列，不删除已有会话。`SessionView`、面试页、复盘页和历史记录都只展示审计元数据，不把整张简历或个人文档证据复制进训练会话。

## 为什么训练来源放在 session，而不是 InterviewEngine

`InterviewEngine` 只负责面试状态机：阶段、问题数、消息和复盘。追问卡、学习计划和 SM-2 属于训练编排上下文，把它们作为 session metadata 保存，可以让状态机保持单一职责，同时让历史记录回答“这次为什么练这个”。

后端路由负责：

1. 验证计划项和追问卡是否属于当前用户；
2. 组装出题上下文；
3. 把来源快照写入 Store。

出题器负责：根据上下文生成有限题目；InterviewEngine 负责：按已有问题推进状态。这三个职责可以分别测试和替换。

## 可用于面试的追问

### 为什么不在前端直接传项目名和简历版本？

因为前端参数是不可信的。前端只传一个卡片 ID，后端在当前用户的当前结构化简历上重新解析，写入项目名和版本。这样既保留可追踪性，也不会因为客户端篡改而读取或记录别人的项目资料。

### 为什么不让追问卡直接修改 SM-2？

点击训练只代表用户选择了一个目标，不代表用户已经回答、更不代表掌握。SM-2 的更新必须依赖真实回答和复盘分数，否则“打开一次卡片”就会污染长期画像。

### 如果卡片焦点和 JD 计划焦点冲突怎么办？

当前实现不静默覆盖，而是带来源标签合并后交给出题器。出题器仍然受到长度和题目数量限制；后续可以根据用户选择或 Agent 计划优先级增加显式权重，但不会改变 session 审计模型。

### 这一步是否已经让项目具备 Agent 能力？

它让 Agent 生成的学习计划真正进入训练执行链路，但卡片入口本身不是 Agent。Agent 的职责仍是读取画像、提出计划并经过确认；专项训练负责执行目标，复盘负责产生反馈，三者通过 focus、plan/item 和 session metadata 连接。

## 验证结果

- 项目追问卡新增 `training_focus`；
- 卡片可以进入专项训练页面，并传递 `question_card_id`；
- 后端拒绝把追问卡绑定到普通简历面试，只允许专项训练；
- 后端验证当前用户的卡片归属，并从服务端补写项目名和简历版本；
- 训练开始时会保留卡片焦点，同时继续读取 JD 学习计划焦点、画像和 SM-2 到期队列；
- 面试页、复盘页和历史记录展示训练来源；
- 暂存工程后端 `43 passed`，Python compileall、前端 typecheck 和生产构建通过。

## 当前限制与下一步

- 追问卡模板仍是确定性的，不会根据具体 JD 自动改变问题措辞；
- 目前需要用户先在专项训练页选择领域，卡片没有强行绑定某个知识领域；
- Agent 尚未提供“从这张卡创建学习计划”的专用受控工具；
- 下一步可以在 Agent 计划工具中增加追问卡引用，并继续加强岗位 focus 与项目字段的匹配解释；真实资料联调、干净环境复现和 GitHub 推送仍需单独确认。
