# Stage24：个人文档引用与重复导入收口

## 目标

让 Personal Agent 的检索结果具备可追踪来源，并避免同一用户反复导入相同资料后产生重复记忆。本阶段不改变 PDF、文本/Markdown、分块或 Embedding 的主接口，只收口文档身份和证据展示。

## 领域规则

### 文档身份

同一用户的“规范化正文”代表一份长期资料。标题和来源类型只是资料元数据，不参与正文去重，因此下面两种操作会返回同一份文档：

```text
保存文本：QTrace 架构说明 + 正文 X
导入 PDF：项目说明.pdf + 抽取正文 X
```

不同用户即使保存完全相同的正文，也仍然是两份互相隔离的个人文档。

### 检索引用

每个检索片段返回一个引用标识：

```text
文档标题#chunk-1 (文档短 ID)
```

它同时表达资料名称、文档块位置和短 ID。Agent 的本地回答会保留这个引用；真实 LLM 会在工具上下文中看到同一字段，并被要求不要编造来源。

## 数据流

```text
新增文本 / PDF
  -> 规范化正文
  -> 计算文档内容指纹
  -> 当前 user_id 下查找同指纹文档
      -> 已存在：返回旧文档，deduplicated=true
      -> 不存在：写入文档和文档块

检索文档块
  -> 相似度排序
  -> 补充 citation
  -> 前端显示引用 / Agent 读取并保留引用
```

去重查询在 SQLite 写事务中执行，避免同一用户的并发导入在检查和写入之间产生明显竞态。旧数据库启动时会为已有个人文档补齐内容指纹，并建立按用户查询的索引。

## 接口变化

`PersonalDocumentView` 新增：

```text
deduplicated: boolean
```

第二次保存相同正文时，接口仍返回 200 和原文档，但 `deduplicated=true`，前端提示“没有重复保存”。

`PersonalDocumentSearchResult` 新增：

```text
citation: string
```

前端检索卡片展示相似度和引用标识；Agent 的规则版回答也会把引用放在证据片段前面。

## 当前取舍

- 只做规范化正文的精确去重，不把“语义相似”误判为同一份资料；
- 不自动覆盖旧标题，不做文档编辑、删除、版本管理和合并；
- 引用使用可读标题、块序号和短 ID，不暴露原始 PDF 路径或文件二进制；
- 不调用外部 Embedding，不把真实资料发送到模型服务；
- 仍然按 `user_id` 隔离文档、指纹和检索结果。

## 面试追问卡

### 为什么要做精确去重？

个人文档会被用户重复导入。重复文档会浪费存储、增加检索噪声，并可能让 Agent 返回多个相同证据。规范化正文指纹可以用很小的接口成本解决这个问题。

### 为什么不直接用 Embedding 判断重复？

Embedding 相似只能说明语义接近，不能证明两份资料完全相同；相似度阈值还会引入误合并。当前先做可解释的精确去重，语义去重可以作为未来独立的审核建议，而不是静默删除资料。

### 引用标识为什么要包含文档块序号？

Agent 只读取相关文档块，不一定读取整份资料。块序号能让用户知道回答依据来自哪一段，也方便后续实现引用跳转或片段高亮。

### 重复导入为什么返回成功而不是报错？

重复导入是幂等行为，不是用户输入错误。返回原文档和 `deduplicated=true`，调用方可以继续使用已有资料，也能在界面上明确告知没有新增记录。

## 验证

- 同一用户相同正文、不同标题和来源类型只保存一条文档；
- 旧版没有 `content_hash` 的个人文档表启动后会自动迁移并补齐指纹；
- 检索结果包含可读引用标识；
- Stub Agent 回答保留引用；
- 前端显示引用和重复保存提示；
- 个人文档、PDF 导入和 Agent 只读链路继续通过回归测试。
