# 阶段 50：本地运行态冒烟检查

## 目标

在不读取数据库、不读取真实简历或个人文档、也不调用外部 API 的前提下，给本地开发环境增加一个可重复的运行态检查。它用于回答“服务是否起来、前端入口是否可访问、生产构建是否带上静态资源”三个问题，不替代完整的浏览器自动化和业务流程验收。

## 实现

新增 `scripts/local_runtime_smoke.py`，默认检查：

1. `http://127.0.0.1:8002/api/health` 是否返回 2xx；
2. `http://127.0.0.1:5174/` 是否返回 2xx；
3. `frontend/dist/index.html` 是否存在，并且其中引用的 `assets/` 文件都存在。

脚本只输出状态码、字节数和资源数量，不输出响应正文、数据库内容、用户资料或异常原文。它使用标准库 HTTP 客户端，因此不引入新依赖；请求地址可以通过命令行参数覆盖，但默认只指向本机。

## 运行方式

在项目根目录执行：

```powershell
python scripts/local_runtime_smoke.py
```

如果前后端已经按本地开发配置启动，同时前端完成过 `npm run build`，预期输出三个 `PASS`。服务未启动时脚本会返回退出码 `2`，这表示运行态条件未满足，不表示代码测试失败。

## 验证结果

- 单元测试使用合成响应和临时 `dist` 目录，不连接真实服务；
- 覆盖本地服务可达、服务不可达和构建资源缺失；
- Python 全量测试、编译检查和前端构建继续作为独立门禁；
- 这一步仍然没有完成真实浏览器自动化，也没有验证真实 LLM、真实 Embedding 或真实个人资料链路。

## 面试追问

### 为什么还要做运行态冒烟，单元测试不够吗？

单元测试验证模块行为，构建检查验证前端能产出静态文件，但端口配置、服务启动和构建产物是否真的可被本地 HTTP 服务访问属于集成边界。冒烟检查用很小的成本把这三个边界显式化，同时保持只读和可重复。

### 为什么不在这个脚本里自动启动服务？

自动启动会引入进程生命周期、端口占用和环境副作用，容易把“服务没启动”掩盖成脚本内部行为。当前脚本只检查开发者已经启动的服务；启动方式仍由 README 和本地环境负责。

### 为什么只检查构建产物引用的资源，不打开所有页面？

这是发布前的快速门禁，不是端到端测试。它首先捕获最常见的空构建、资源路径错误和服务未启动问题；业务页面的登录、Agent 重试和计划确认仍需要后续人工演示或专门的浏览器测试。
