# 阶段 66：前端认证状态生命周期

## 目标

阶段 65 证明了 token 如何进入 HTTP 请求，本阶段继续追踪 token 在前端应用中的生命周期：首次加载、认证成功、账户校验失败、退出登录和页面访问门禁。检查仍然只读源码，不输入密码、不读取浏览器存储，也不执行真实登录。

## 代码证据

`frontend/src/App.tsx` 当前有一条明确的认证状态链：

1. 应用启动时从固定的 `TOKEN_KEY` 读取本地 token，并用它决定是否需要加载账户。
2. 登录或注册成功后，把后端返回的 token 写入本地状态和本地存储，再进入账户加载流程。
3. `/me` 或 `/settings` 加载失败时，清除 token、用户和设置状态，回到登录入口，而不是继续展示可能过期的业务页面。
4. 用户主动退出时清除 token、用户和设置状态。
5. 在 `token` 或 `user` 缺失时渲染 `LoginPage`；在账户配置尚未加载时停留在 loading/onboarding 状态，业务路由只在认证状态完整后开放。

`scripts/frontend_route_preflight.py` 新增 `REQUIRED_AUTH_STATE_MARKERS`，只读检查上述生命周期标记；`tests/test_frontend_route_preflight.py` 覆盖完整契约和缺失标记两种情况。它与认证页面、统一 API client、业务路由和 Agent 恢复交互检查一起运行。

## 工程取舍与安全边界

当前本地学习项目使用 `localStorage` 保存访问 token，优点是实现简单、刷新页面后可以恢复本地演示账号；代价是如果页面存在 XSS，脚本可能读取 token。生产系统通常会优先考虑 HttpOnly/Secure/SameSite Cookie、短时访问 token、刷新 token 轮换、CSRF 防护和更严格的内容安全策略，具体方案取决于部署形态。

因此，本阶段可以证明前端状态转换和失效回退路径被源码契约保护，但不能证明生产级认证安全、token 加密、跨设备会话管理、过期刷新或完整浏览器 E2E。

## 面试讲解

可以这样回答“刷新页面或 token 失效时怎么办”：

> 应用启动先读取本地 token，然后并行请求当前用户和模型设置。只要其中一个请求失败，就清除 token、用户和设置状态，让界面回到登录页；只有 token 和 user 都存在，并且配置状态已加载，才渲染业务路由。这样过期 token 不会继续驱动业务请求，也不会把失败伪装成已登录。当前实现为了本地学习简单使用 localStorage，若进入生产会评估 HttpOnly Cookie、刷新机制和 XSS/CSRF 防护。

## 验证结果

- 前端路由预检新增 `auth state markers` 检查。
- 新增回归验证认证状态生命周期标记缺失时会被报告。
- 本阶段不修改后端认证接口、数据库模型、模型调用或真实账号数据。
