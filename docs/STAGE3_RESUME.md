# 阶段 3：PDF 简历链路

## 目标

把原项目中的“简历作为面试上下文”拆成一条可以独立解释和验收的链路：

```text
浏览器选择 PDF
  -> multipart 上传到 FastAPI
  -> 按 user_id 保存到本地目录
  -> pypdf 提取文本
  -> 启动面试时读取文本
  -> provider opening / question / review 获得简历上下文
```

这一步没有把简历做向量化。参考项目的面试主链直接读取简历文本，而主题知识才进入后续的检索链路；两者的用途不同。

## 代码职责

| 文件 | 责任 |
| --- | --- |
| `backend/resume.py` | 文件名、大小、PDF 签名、用户目录、解析、替换旧文件 |
| `backend/main.py` | 鉴权、上传/状态/下载/删除路由，以及启动面试时注入文本 |
| `backend/models.py` | 简历状态和文本响应模型 |
| `frontend/src/api.ts` | JSON 请求与 `FormData` 上传的区别 |
| `frontend/src/App.tsx` | 训练页上传控件、状态提示和删除确认 |

## 数据隔离

文件路径是：

```text
<数据目录>/users/<user_id>/resume/<原始文件名>.pdf
```

每个用户只保留当前的一份 PDF。所有接口都先通过 Bearer token 得到用户，再把 `user_id` 传入服务层；客户端不能通过参数读取另一个用户的文件。

上传时会检查：

- 文件名不能包含路径分隔符；
- 扩展名必须是 `.pdf`；
- 大小不能超过 20 MB；
- 前 1 KB 中必须出现 `%PDF-`；
- 新文件先解析成功，再替换旧文件，避免坏文件覆盖已有文件。

这些检查是“应用层边界”，不是完整的恶意 PDF 防护。生产环境还需要更严格的隔离、病毒扫描、配额和权限策略。

## 为什么简历文本不进入 Embedding

面试官的问题需要围绕候选人的完整经历进行生成，直接把简历文本作为上下文更简单，也更容易保证关键经历没有因为切块或相似度检索被漏掉。主题知识库则适合通过关键词/向量召回少量相关知识，两条链路不应该混为一谈。

## 面试追问卡

### 1. 为什么前端上传不能直接设置 `Content-Type: application/json`？

因为文件上传使用 `multipart/form-data`，边界字符串需要由浏览器自动生成。客户端检测到 `FormData` 时不设置 JSON 头，否则 FastAPI 无法解析文件字段。

### 2. 为什么服务端仍然提供文本输入？

PDF 解析可能遇到扫描件、复杂排版或解析失败。文本输入是可解释的降级路径；如果请求中显式填写文本，就优先使用它，否则才读取用户保存的 PDF。

### 3. 为什么保存前先解析？

仅检查 `%PDF-` 只能说明文件看起来像 PDF，不能说明结构可读。先用 `pypdf` 解析临时文件，成功后再原子替换，可以减少“上传成功但面试启动才失败”的延迟错误。

### 4. 简历文本会不会存进数据库？

本重建版本把 PDF 保存在用户目录，会话状态只保存启动时传给状态机的 `resume_text`，用于让历史会话可复现。真实系统需要进一步评估敏感信息加密、保留期限和日志脱敏。

### 5. 这一步和 RAG 有什么关系？

它先解决“候选人自身上下文”的读取问题，不等于完成 RAG。RAG 还需要文档切块、索引、召回、上下文拼接和评估；这些会在主题知识库阶段单独实现。
