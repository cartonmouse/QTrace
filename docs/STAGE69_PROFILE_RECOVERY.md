# 阶段 69：画像页可恢复加载

## 发现的问题

阶段 68 已经把画像待复习项接到专项训练，但画像页的初始加载仍然缺少错误分支：`/profile` 或 `/topics` 任一请求失败时，页面会一直显示“正在读取画像…”，用户不知道发生了什么，也没有重试入口。

## 实现

`ProfilePage` 现在把加载状态分成三种：

```text
请求中       -> 正在读取画像…
请求失败     -> 画像加载失败 + 错误信息 + 重新加载画像
请求成功     -> 画像指标、SM-2 队列和“立即复习”入口
```

- `/profile` 与 `/topics` 仍然并行请求；任一失败都会进入可观察的错误状态；
- 用户点击“重新加载画像”只增加本地 `loadKey`，重新执行同一组请求，不改变 token、画像数据或后端状态；
- 成功结果仍然复用阶段 68 的 SM-2 待复习项直达专项训练链路；
- 错误卡使用 `role="alert"`，让辅助技术能够感知加载失败，不把失败伪装成空画像。

## 预检与回归

`scripts/frontend_route_preflight.py` 新增 `REQUIRED_PROFILE_RECOVERY_MARKERS`，只读检查错误标题和重试入口；`tests/test_frontend_route_preflight.py` 新增缺失画像恢复标记的回归。前端 typecheck/build 验证状态和 JSX 结构。

这不是浏览器 E2E：它不能证明真实网络断开时的视觉效果、重试请求成功或错误信息符合所有供应商响应；后续人工彩排仍需使用合成账号。

## 面试讲解

可以这样回答“页面请求失败时怎么处理”：

> 画像页把 profile 和 topics 当成一次加载事务。请求期间显示 loading；任一请求失败就展示可观察的错误卡和重试按钮，而不是把空数据渲染成“没有画像”。重试只重新发起读取，不写数据库、不改变学习计划，也不会绕过认证。成功后，原来的 SM-2 队列和直达专项训练入口继续复用。

## 边界

- 没有读取或输出 API Key，没有读取或上传真实简历、个人文档或数据库内容。
- 没有调用外部 API、输入密码、部署、删除文件或提交推送 GitHub。
- 本阶段只改善画像页的前端加载可恢复性，不修改画像计算、SM-2 算法或后端接口。
