# 阶段 7：JD 导入与岗位定向训练

## 目标

把泛化模拟面试变成面向具体岗位的一轮训练：

```text
输入公司 / 岗位 / JD
  -> 本地可解释分析器提取技术重点
  -> 结合简历生成匹配证据和风险缺口
  -> 生成岗位问题蓝图
  -> 合并今日待复习项
  -> 复用 InterviewEngine 开始定向训练
  -> 训练记录保存 JD 快照，历史可追溯
```

参考项目的 JD 备面包含“先分析、再出题、最后评估”的独立流程。本阶段先保留这个产品顺序，但把第一版分析器做成确定性的本地模块，避免没有真实 LLM 时无法运行，也让每个结果都能解释和测试。

## 岗位分析器

`backend/jd.py` 维护一个小型 `SKILL_CATALOG`，目前覆盖 Python、FastAPI、RAG、Agent、LLM、Embedding、SQL、Redis、Docker、Kubernetes、性能和评测等关键词。

分析器输出：

- `focus_areas`：命中频率最高的技术重点和优先级。
- `likely_question_groups`：核心技术、工程化、岗位匹配、反问四类问题组。
- `resume_alignment`：简历命中的技术点、可能的风险缺口和推荐故事方向。
- `prep_priorities`：面试前可以直接执行的准备事项。
- `question_blueprint`：覆盖岗位匹配、技术深挖、项目、场景、质量、协作和反问的 8 个问题。

这是“规则分析器”，不是完整的 LLM 语义理解。它的价值是先把接口、数据流和可观测结果搭起来；未来可以只替换 `analyze_jd`，保持路由和 `InterviewEngine` 不变。

## 接口

- `POST /api/job-prep/preview`：输入 `company`、`position`、`jd_text`、`use_resume`，返回岗位拆解。
- `POST /api/job-prep/start`：使用拆解结果创建 `mode=jd_prep` 的面试会话。
- 原有 `/api/interview/{session_id}/answer`、`finish`、`history` 继续复用。

专项训练和 JD 定向训练的区别是：专项训练的 `topic` 指向一个知识领域；JD 定向训练没有固定知识领域，而是把 JD 分析结果放进 `knowledge_context`，并把岗位问题蓝图放进 `question_bank`。

## 数据持久化

`sessions` 新增：

| 字段 | 含义 |
| --- | --- |
| `company` | 公司名称 |
| `position` | 岗位名称 |
| `jd_text` | 本轮使用的完整 JD 快照 |
| `jd_preview_json` | 分析结果快照 |

保存快照的原因是：JD 可能会被修改，同一轮训练必须能解释“当时系统依据的是什么”。旧数据库通过 `ALTER TABLE` 自动补齐默认值。

## 面试追问卡

### 1. 为什么不直接把 JD 拼到 prompt？

直接拼接只能让模型“看到材料”，不能明确岗位重点、简历缺口和训练顺序。先形成结构化 preview，后续的出题、界面展示和复盘都可以复用同一份中间结果。

### 2. 为什么先做规则分析，而不是直接接 LLM？

规则版不依赖 API key，输出稳定，适合先验证数据流和前端交互；真实 LLM 接入后可以替换分析器，不必重写会话状态机。面试时要明确说明这是学习版的工程取舍。

### 3. JD 定向训练为什么复用原有状态机？

“岗位来源”与“对话推进”是两个维度。`jd_prep` 只改变上下文和问题池，回答、阶段推进、结束、复盘仍是同一个 `InterviewEngine`，避免为每个入口复制一套会话逻辑。

### 4. 为什么保存 JD 快照？

为了历史可重放和问题可解释。若只保存岗位名称，之后无法知道某道题是根据哪一版职责或技术要求生成的。

## 当前限制与下一步

- 当前分析器主要依赖关键词，无法可靠理解同义表达、隐含职责和上下文优先级。
- JD 定向训练暂时复用 StubProvider 的结构化问题池，没有参考项目那样的独立逐题批量评估页面。
- 下一步可以接入真实 LLM 生成 preview 和问题，同时保留本地规则版作为降级路径；之后再实现录音转写与复盘。
