# 阶段 51：干净环境复现准备与面试演示脚本

## 目标

把“项目能运行”和“我能讲清楚项目”拆成两条可检查的线：

- `scripts/reproduction_preflight.py` 只读检查未来干净环境复现需要的核心文件、前端脚本和本地数据忽略规则；
- 本文固定面试演示顺序、每一步要展示的证据和面试官可能追问的回答边界。

本阶段是准备工作，不执行新的依赖安装、GitHub 克隆、外部部署或正式干净环境复现；这些动作等项目完整后再单独确认。

## 复现前自检

在项目根目录运行：

```powershell
python scripts\reproduction_preflight.py
python scripts\repository_preflight.py
```

第一个脚本确认仓库结构、`frontend/package.json` 中的 `dev/typecheck/build` 脚本以及 `.env`、`data/`、`node_modules`、`dist` 忽略规则。第二个脚本继续检查明显密钥模式和本地日志/数据库产物。两个脚本都是只读检查，不读取 SQLite 内容、不读取真实简历或个人文档、不调用外部 API。

## 未来的干净环境复现顺序

这是一份待执行清单，不是本阶段已经完成的验证：

1. 准备 Python 3.11+、Node.js/npm 和一个新的工作目录；
2. 获取 GitHub 仓库后进入 `rebuild` 目录；
3. 创建虚拟环境，安装 `requirements.txt`；
4. 在 `frontend` 目录执行 `npm ci`；
5. 先运行后端测试、Python 编译检查和前端 typecheck/build；
6. 分别启动 `127.0.0.1:8002` 后端和 `127.0.0.1:5174` 前端；
7. 运行 `scripts/local_runtime_smoke.py`，确认三个本地门禁均为 `PASS`；
8. 用合成账号和本地 StubProvider 演示登录、训练、Agent 草稿和失败恢复；
9. 只在结果、依赖版本和启动说明都稳定后，再考虑真实资料联调和 GitHub 版本整理。

复现时不把真实简历、真实录音、API Key 或个人文档放进仓库。真实 LLM/Embedding 不是“仓库能否启动”的必要条件；它们属于单独的用户级配置和联调范围。

## 15 分钟面试演示顺序

### 1. 先讲问题和边界（1 分钟）

“QTrace 是一个面向求职训练的个人 Agent 系统。它把结构化简历、知识图谱、训练历史、画像和 SM-2 到期复习项组合成下一步训练建议；Agent 负责读取上下文和提出学习计划，但写操作必须先生成 draft，再由用户确认。”

同时主动说明：当前复现项目以文本为主，真实长音频、说话人分离、时间戳对齐、外部部署和 WebSocket 实时辅助不在当前交付范围。

### 2. 展示最小主链（3 分钟）

使用合成的项目资料完成：本地注册/登录 -> “模型设置”启用 StubProvider -> 简历编辑器保存一个项目 -> 进入项目追问卡或专项训练。重点展示追问卡不是随机文案，而是从项目字段生成背景、职责、设计、验证和取舍五类问题。

### 3. 展示图谱与 SM-2（3 分钟）

进入知识库创建或选择一个训练主题，再打开知识图谱。指出：图谱是由题库、画像和复习事实即时计算出的只读视图；问题节点可以精确进入训练，相近问题只是可选候选；SM-2 到期项解释“为什么今天优先练这道题”，不会因为打开图谱就直接修改状态。

### 4. 展示 Agent 的工具链（4 分钟）

进入 Personal Agent，提出“根据我的项目追问和近期复习安排一个训练计划”。讲解规划/回答两步边界：先由模型或 Stub 形成受控工具调用，再由后端按当前用户读取画像、到期复习、近期训练、简历/图谱上下文，最后生成回答。计划写入数据库时只产生 `draft`，用户点击确认后才成为可执行计划；计划项进入专项训练时会保留来源审计。

### 5. 展示失败恢复（2 分钟）

用 fake provider 的合成失败测试说明两类情况：规划或回答失败时，后端返回稳定错误码，前端删除未持久化的乐观消息并恢复输入；如果回答失败前已经产生计划草稿，则返回 `preserved_draft` 和已验证的对话 ID，前端只加载该对话下的 draft，不会随便加载最新计划。重试由用户点击触发，不自动循环。

## 面试官追问速答

### 为什么要有 Agent，普通工作流不行吗？

普通工作流适合固定步骤，Agent 适合根据用户当前目标选择只读工具并组织上下文。但真正的业务写入仍由后端白名单、用户归属和 draft/confirm 状态机控制，模型不能直接执行任意 SQL 或修改画像。

### 为什么图谱不直接使用向量数据库？

当前图谱的目标是可解释和可复现，所以关系边由题目 token/中文二元片段等确定性规则计算；Embedding 用于个人文档检索，是另一条可替换的证据召回链路。两者职责分开，便于测试和解释。

### SM-2 和画像分别解决什么问题？

画像描述较长期的强项、薄弱点和行为信号；SM-2 解决某个复习项何时再次出现。出题器把画像、到期项、近期训练和用户显式焦点合并，但训练开始不会直接假设用户已经掌握。

### 如果模型或工具失败，系统怎样保证不乱写？

模型规划/回答失败返回稳定错误协议；只读工具失败可以带安全摘要继续回答，但不能把缺失上下文当成零值；学习计划写工具声明了画像、复习队列和近期训练等前置依赖，依赖失败时只记录 skipped，不写 draft。

### 这个项目目前最诚实的不足是什么？

没有把未完成能力包装成已完成：独立浏览器自动化、真实长音频链路、多 Agent 并行 Copilot、WebSocket 实时辅助、正式干净环境复现和外部部署仍是后续工作。当前证据主要是后端回归、前端构建、只读运行态检查和本地人工演示。
