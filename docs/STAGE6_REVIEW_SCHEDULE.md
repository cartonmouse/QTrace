# 阶段 6（续）：间隔复习与今日训练队列

## 目标

让“薄弱点”不只是画像页上的静态文字，而是能决定下一次训练先练什么：

```text
训练结束
  -> 复盘产出 weak_points
  -> review_items 保存每个薄弱点的排期状态
  -> 新薄弱点立即进入今日队列
  -> 下一次专项训练优先把到期薄弱点放入题库
  -> 新一轮得分更新间隔和难度因子
```

## 数据模型

新增 SQLite 表 `review_items`，唯一键是 `user_id + topic + point`：

| 字段 | 含义 |
| --- | --- |
| `topic` | 所属领域；简历训练产生的通用问题使用空字符串 |
| `point` | 复盘抽取的薄弱点文本 |
| `interval_days` | 当前复习间隔 |
| `ease_factor` | 根据答题质量调整的难度因子，最低 1.3 |
| `repetitions` | 连续成功记忆次数 |
| `next_review` | 下一次应复习的日期 |
| `last_score` | 上一次用于调度的 0—10 分数 |

这个表和 `topic_profiles` 分工不同：`topic_profiles` 记录“这个领域练得怎么样”，`review_items` 记录“某个具体薄弱点什么时候再练”。

## 调度规则

`backend/review_schedule.py` 把 0—10 分映射为 SM-2 的 0—5 质量分：

- 新发现的薄弱点：今天可复习，避免刚发现的问题被遗忘。
- 成功回忆：间隔按 `1 天 -> 3 天 -> interval * ease_factor` 增长。
- 低于 6 分：视为回忆失败，连续次数清零，明天重新复习。
- `ease_factor` 最低为 1.3，避免间隔无限缩短或出现异常值。

这是一版学习用的透明实现，不声称已经复现参考项目全部的遗忘曲线、向量相似度匹配或题目难度校准。

## 关键接口和调用链

- `GET /api/profile`：在全局画像之外返回 `due_reviews`。
- `GET /api/profile/due-reviews?topic=rag`：按领域查看今天到期的薄弱点。
- `POST /api/interview/start`：专项训练启动时读取到期项，把它们排在高频题库之前。
- `POST /api/interview/{id}/finish`：第一次生成复盘时写入或更新调度状态。

前端画像页的 “TODAY'S REVIEW QUEUE” 是读模型；专项训练页显示当前领域的到期项数量。真正的训练内容仍然由同一个 `InterviewEngine` 推进，调度器只负责选择输入，不改变状态机职责。

## 面试追问卡

### 1. 为什么不能只保存一个总掌握度？

总掌握度回答“整体怎么样”，但无法回答“RAG 的 chunk 策略明天是否应该复习”。具体薄弱点需要独立的下一次复习日期和连续成功次数。

### 2. 为什么新薄弱点要立即到期？

复盘第一次发现问题时，系统还没有足够的成功回忆样本去估计间隔。先放入今日队列是保守策略，下一轮结果再决定是否延长间隔。

### 3. 为什么把调度器做成独立纯模块？

日期计算和 SM-2 规则不应该依赖 FastAPI、SQLite 或 React。独立模块可以用固定日期做单元测试，也方便未来替换为更完整的调度算法。

### 4. 如果同一个薄弱点的文字稍有变化怎么办？

当前版本使用标准化后的文本精确匹配，优点是可解释、容易验证；生产版本可以用 embedding 相似度或人工归并解决“回答缺少事实细节”和相近表达被拆成多个条目的问题。

## 当前限制与下一步

- 当前分数来自 StubProvider 或外部模型复盘，尚未建立盲评数据集验证调度是否真正提升记忆效果。
- 薄弱点仍是文本精确匹配，没有 embedding 去重、题目难度和知识点图谱。
- 下一步可以做 JD 导入与岗位定向训练，把岗位要求和今日复习队列合成一套更接近真实面试的训练计划。
