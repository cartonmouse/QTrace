# 阶段 70：专项训练页可恢复加载

## 目标

阶段 68 已经把画像中的 SM-2 到期复习项接入专项训练，阶段 69 又补了画像页的加载错误和重试入口。本阶段继续沿着同一条个性化学习闭环，处理专项训练页初始读取失败时的用户体验：训练领域、到期复习队列或图谱问题读取失败时，页面不能把失败误显示成“还没有训练领域”，也不能让开始按钮一直处于不可解释的禁用状态。

## 实现

- `TopicDrillPage` 增加 `loading` 和 `loadKey` 状态；初次进入或点击重试时，重新读取训练领域、SM-2 到期复习项和可选图谱问题。
- 请求成功后沿用原来的主题选择逻辑：优先保留 URL 中的 `topic`，其次按领域名称匹配，最后选择第一个领域；已有 `focus`、计划、追问卡和图谱来源参数不变。
- 请求失败时清空本次页面的读模型，并展示 `role="alert"` 错误卡与“重新加载训练领域”按钮；重试只重复读取，不创建 session、不修改画像、不推进 SM-2。
- 用 `active` 标记忽略卸载后的异步结果，避免用户快速切换路由后旧请求覆盖新页面状态。
- `frontend_route_preflight.py` 和回归测试新增专项训练恢复标记；最终交付预检把阶段文档纳入必需材料。

## 证据与边界

本阶段的自动化证据是源码契约、TypeScript 类型检查、前端构建和 Python 回归。它能证明失败状态和无副作用重试入口没有被误删，但不能证明浏览器真实网络断开、密码登录、视觉布局或后端服务故障下的完整 E2E 行为。人工浏览器彩排仍使用全新的合成数据库，且需要用户临时确认密码输入。

专项训练开始时，后端仍会重新校验主题、焦点、计划项、追问卡和图谱问题归属；前端只负责把入口上下文带过去，不能被视为权限边界或事实来源。

## 面试讲法

> 我把专项训练页的读取状态拆成 loading、成功和失败三态。因为“请求失败”和“用户还没有创建领域”是两种完全不同的事实，不能都渲染成空列表。失败时前端只清理当前页面的读模型并显示可重试错误卡，重试再次读取领域、复习队列和可选图谱问题，不产生数据库副作用；真正开始训练时，后端仍会做主题和来源参数校验。

## 当前限制

- 登录提交、业务页面人工点击、正式全新目录复现、公开发布和 GitHub 提交推送仍需用户确认；
- 未新增真实数据、真实 LLM/Embedding 网络调用、WebSocket、音频采集或外部部署能力；
- 页面恢复契约仍不是生产级离线缓存、请求取消、重试退避或 token 刷新方案。
