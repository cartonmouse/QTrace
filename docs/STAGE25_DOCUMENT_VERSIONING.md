# Stage25：个人文档版本管理与引用版本号

## 目标

Stage24 已经解决了“同一份资料重复导入”和“检索结果来自哪里”的问题，但文档仍然不能编辑。若直接覆盖 `personal_documents.content`，旧项目说明和旧复盘就会丢失，引用也可能无法解释当时使用的是哪一版内容。

本阶段增加一条最小、可解释的版本链路：

- 新建文档从 `v1` 开始；
- 内容发生变化时保存为 `v2`、`v3`……，旧版本只读保留；
- 当前列表和检索只使用最新版本；
- 引用从 `标题#chunk-1` 升级为 `标题#v2-chunk-1`；
- 前端可以查看版本历史，载入任意历史版本并保存为新的最新版本。

本阶段仍然不接入真实资料、外部 Embedding、OCR 或 GitHub 推送。

## 领域规则

### 文档与版本是两个层次

`personal_documents` 表表示“这份长期资料当前是什么状态”，保留当前版本号、当前正文和当前检索块。`personal_document_versions` 表表示“这份资料过去经历过什么变化”，每一行是不可变的正文快照。

```text
Document  QTrace 项目架构说明
  ├── v1  初始架构说明
  └── v2  增加 Agent 工具链后的架构说明（当前）
```

文档 ID 在编辑过程中不变，版本号单调递增。这样既能让外键、前端选中状态和引用中的文档短 ID保持稳定，也能让历史内容被精确取回。

### 什么变化会产生新版本

标题、来源类型或规范化正文任一发生变化，都可以保存为新的版本；当前实现仍然使用正文内容指纹判断“是否真的没有变化”：

- 正文指纹不变：返回当前版本并标记 `unchanged=true`，不产生新版本；
- 正文指纹变化：创建下一个版本，删除旧的当前检索块并写入新版本块；
- 旧版本的正文和元数据进入版本快照表，不再参与当前检索。

标题改变但正文不变不会制造无意义的版本，这与 Stage24 的“正文决定文档身份”规则一致。

### 当前检索为什么只读最新版本

如果历史版本和当前版本同时参与检索，同一项目事实可能出现多份相互矛盾的答案，Agent 还需要额外判断哪一版有效。当前选择“默认检索最新、历史按用户主动查看”的策略：

```text
编辑保存
  -> 版本快照写入 personal_document_versions
  -> 当前文档指针更新到 vN
  -> 删除旧 document_chunks
  -> 生成 vN 的新 chunks
  -> 检索只 join 当前 document_chunks 和 personal_documents.version
```

未来如果需要“比较两版项目经历”或“按时间回看训练资料”，可以在版本接口上增加专门的 diff/历史检索，而不改变默认 Agent 证据边界。

## 数据库迁移

旧库可能只有 Stage24 的 `personal_documents` 表，因此启动迁移需要做到增量兼容：

1. 为当前表补充 `version INTEGER NOT NULL DEFAULT 1`；
2. 创建 `personal_document_versions` 和按用户/文档/版本倒序的索引；
3. 为已有文档补写 `v1` 快照；
4. 保留 Stage24 的 `content_hash` 回填和去重索引。

迁移不删除旧字段、不重建用户数据；同一份旧正文可以在启动后立即被读取、检索和编辑。

## 接口

```text
PUT /api/agent/documents/{document_id}
GET /api/agent/documents/{document_id}/versions
GET /api/agent/documents/{document_id}/versions/{version}
```

更新接口沿用新增文档的标题、正文和来源类型校验。所有查询都带当前 `user_id`：其他用户即使知道文档 ID，也只能得到 404，不能读取版本正文。

列表接口只返回版本元数据；只有用户明确请求某个版本时，详情接口才返回正文。这减少了默认页面的数据量，也避免把全部历史内容无意传到前端。

## 事务与一致性

一次更新在 SQLite `BEGIN IMMEDIATE` 事务中完成：

1. 锁定并读取当前用户拥有的文档；
2. 判断正文指纹是否变化；
3. 写入新版本快照；
4. 删除该文档的旧当前块；
5. 更新当前文档指针和统计信息；
6. 写入新版本的分块和本地向量。

任何一步失败，事务回滚，不会出现“当前文档已经是 v2，但 v2 的分块没有写完”的半成品状态。旧版本表不参与删除当前块，因此历史快照仍可读取。

## 前端行为

- 文档卡片显示当前版本号；
- “版本历史”按钮加载版本元数据；
- 选择历史版本会把正文放入编辑器，但不会自动保存；
- 编辑器明确显示“保存为新版本”，避免用户误以为是在覆盖旧资料；
- 检索卡片显示版本号和引用，例如 `QTrace 项目架构说明#v2-chunk-1 (a1b2c3d4)`。

## 面试追问卡

### 为什么不直接覆盖当前文档？

直接覆盖会丢失历史事实，旧的 Agent 回答也无法解释当时依据的材料。版本快照把“当前可检索状态”和“历史可审计状态”分开，既保证默认检索简单，又保留复盘能力。

### 为什么文档 ID 不随版本变化？

文档 ID 表示同一份长期资料，版本号表示这份资料的时间状态。如果每次编辑都创建新文档，引用、前端状态和去重关系都会变复杂；稳定文档 ID加单调版本号更容易维护。

### 为什么用内容指纹判断 unchanged，而不是比较 Embedding？

Embedding 是有损的相似表示，不能准确证明正文没有变化。标题和空白规范化后计算 SHA-256，成本低、结果确定，可用于幂等判断；Embedding 继续只负责检索，不负责身份和版本判定。

### 为什么历史版本默认不参与检索？

默认回答应优先使用用户当前认可的资料，历史版本可能包含已经过期的技术方案。历史检索应当是用户主动发起的另一种场景，避免默认回答混入过期证据。

### 如何保证不同用户不能读取版本？

版本查询同时约束 `user_id` 和 `document_id`，而不是只按文档 ID查询；更新、版本列表和版本详情都经过同一个用户鉴权边界。没有匹配记录时统一返回 404，不暴露文档是否属于其他用户。

## 验证结果

- 同一用户的新增文档从 `v1` 开始；
- 修改正文生成 `v2`，版本列表按新到旧返回；
- `v1` 和 `v2` 的正文可以分别读取；
- 当前检索只返回 `v2` 的分块，并生成 `#v2-chunk-1` 引用；
- 相同正文再次保存返回 `unchanged=true`，版本号不增长；
- 旧表启动迁移自动补齐 `version`、版本表和 `v1` 快照；
- 暂存工程完整后端测试 `41 passed`；Python compileall、前端 typecheck 和生产构建通过。

## 当前限制与下一步

- 版本历史目前没有文本 diff、回滚按钮和删除/归档策略；
- 当前仍只保留 PDF 抽取后的文本，不保留原始 PDF 二进制；
- 检索继续使用本地确定性向量，不代表真实语义 Embedding 质量；
- 下一阶段优先实现结构化简历编辑器，让“个人文档版本链路”与“简历字段版本”形成可演示的编辑闭环；真实资料联调和外部 Embedding 仍需单独确认。
