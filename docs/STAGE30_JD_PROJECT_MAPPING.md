# Stage30：JD 与项目追问映射

## 目标

JD 定向备面已经能识别岗位中的 Python、RAG、Agent、评测等技术词，但过去的“简历匹配”只是统计简历全文是否出现同一个词，无法回答一个更重要的问题：这个岗位要求，应该用简历中的哪个项目来证明？

本阶段在结构化简历存在时，把 JD 技能映射到项目字段，并返回一个可继续执行的代表性项目追问卡。映射是确定性的证据提示，不是 LLM 对候选人的录用判断。

## 数据链路

```text
JD 文本
  -> SKILL_CATALOG 识别岗位技能
  -> 结构化简历 projects
  -> description / role / technologies / highlights 别名匹配
  -> project_matches
  -> 返回命中技能、证据字段和 question_card_id
  -> 用户从 JD 页面进入 Agent
  -> Agent 验证追问卡并生成 draft 训练计划
```

示例返回：

```json
{
  "project_name": "问迹 QTrace",
  "focus_area": "Agent",
  "matched_skills": ["Agent", "FastAPI"],
  "evidence_fields": ["role", "technologies", "highlights"],
  "question_card_id": "project-1-question-3",
  "reason": "项目的 role、technologies、highlights 字段命中 Agent、FastAPI；建议用该项目回答岗位技术落地和验证问题。"
}
```

## 为什么只使用结构化简历

项目映射需要知道“哪个字段命中”。PDF 简历已经被提取成一段文本，缺少可靠的项目边界和字段来源；如果此时让系统猜测项目名和职责，匹配结果无法解释。因此：

- 用户勾选简历联动且结构化简历存在时，返回项目映射；
- 只有 PDF 或显式关闭简历联动时，仍然可以做普通 JD 技能分析，但 `project_matches=[]`；
- 没有命中时返回空列表，并提示用户补充技术栈或关键工作；
- 不把匹配结果写入画像、复习队列或简历版本。

这让“没有匹配”成为诚实的准备信号，而不是让模型为了填满页面编造项目相关性。

## 匹配规则

复用已有的 `SKILL_CATALOG`，每个技能包含规范名称、别名和类别。对每个项目，把字段分别转换为可检索文本：

- `description`：项目解决的问题和边界；
- `role`：候选人的职责；
- `technologies`：使用的技术；
- `highlights`：关键工作、结果和验证。

如果 JD 命中的技能别名出现在项目字段中，就记录技能和字段。匹配结果最多返回 8 个项目，技能和字段都做去重。没有使用 Embedding 或 LLM，因此同一输入每次结果稳定，面试时可以清楚说明“为什么命中”。

## 代表性追问卡

一个项目可能有五张卡，但岗位技能映射需要一个可执行入口：

- 一般技能命中使用“关键设计”卡 `question-3`，重点追问技术选择、架构和取舍；
- 命中“评测”或“性能优化”时使用“效果验证”卡 `question-4`，把岗位要求落到指标、基线和故障验证；
- 卡片 ID 只是入口，进入 Agent 后仍由后端验证当前用户和简历版本；
- Agent 计划不会自动确认，也不会因为岗位命中就修改 SM-2。

这是一种最小的 seam：JD 的关注点进入项目卡，再进入 Agent 计划和专项训练，仍然复用已有的状态机和权限边界。

## 页面行为

JD 定向备面页面新增“JD → 项目追问映射”区域：

- 展示项目名、岗位 focus、命中技能和命中字段；
- 展示确定性解释，帮助候选人知道面试回答应引用哪些简历字段；
- 提供“让 Agent 围绕项目制定计划”按钮，携带代表性卡片 ID；
- 没有结构化项目命中时明确提示补充项目字段，而不是显示一个虚假的匹配项目。

## 可用于面试的追问

### 为什么不直接用 LLM 判断简历项目和 JD 是否匹配？

因为第一版要先保证可解释和可回归。技能词和字段命中能给出直接证据，适合做基础版本；以后可以让 LLM 负责对已命中的证据生成解释，但不应替代来源校验。

### 为什么“命中关键词”不能直接说明候选人适合岗位？

关键词只能证明文本存在，不能证明深度、职责边界或结果。页面把匹配结果称为准备建议，并继续引导用户回答项目职责、设计、验证和复盘追问，不输出录用结论。

### 为什么命中评测时选择“效果验证”卡？

因为评测和性能要求最终需要通过指标、基线、压测或失败样本验证。选择代表性卡只是减少一次点击，其他四类卡仍然存在，用户可以继续完整准备项目故事。

### 这一步是否接入了向量数据库？

没有。JD 项目映射使用小型技能别名表和结构化字段匹配；个人文档检索仍然是另一条本地确定性 Embedding 链路。把“岗位匹配”和“个人证据检索”分开，便于单独替换和测试。

## 验证结果

- 结构化项目中的 Python、FastAPI、Agent 等字段可以命中对应 JD 技能；
- 返回项目名、命中技能、证据字段、解释和代表性追问卡 ID；
- 关闭简历联动时不生成项目匹配；
- JD 页面可以把命中的卡片交给 Agent 计划入口；
- 暂存工程后端 `45 passed`，Python compileall、前端 typecheck 和生产构建通过。

## 当前限制与下一步

- `SKILL_CATALOG` 仍是小型人工词表，无法覆盖所有公司内部术语、同义表达和中文缩写；
- 只做字段级关键词命中，还没有语义相似度、重排或匹配置信度；
- 一个项目只返回一张代表性卡片，尚未提供“按每个 JD focus 生成完整卡片集合”；
- 下一步可以补充岗位 focus 权重和用户可确认的匹配解释，再统一进行干净环境复现；真实资料联调、外部部署和 GitHub 推送仍需单独确认。
