# Stage31：JD focus 权重与项目匹配评分

## 目标

Stage30 已经能够回答“哪些项目命中了 JD 技能”，但多个项目同时命中时，页面没有说明先准备哪个项目。本阶段增加岗位 focus 优先级和字段权重，得到稳定、可解释的项目排序。

## 评分输入

每个 JD 技能由 `SKILL_CATALOG` 命中后进入 `focus_areas`。当前优先级由 JD 中技能出现顺序决定：前两个为 `high`，接下来两个为 `medium`，其余为 `normal`。项目匹配时使用：

```text
项目分数 = JD 技能出现次数 × 2
         + 岗位优先级权重（high=2, medium=1, normal=0）
         + 命中字段权重之和
```

字段权重：

- `technologies = 3`：直接说明使用过什么技术；
- `role = 2`：说明候选人是否亲自负责；
- `highlights = 2`：说明做过什么关键工作或结果；
- `description = 1`：说明项目背景，但不单独证明技术深度。

同一项目命中多个 JD 技能时，分数累加；项目按总分降序返回。结果同时保存最高优先级和命中的字段，页面可以把数字解释回具体证据。

## 为什么不用一个黑盒相似度

项目匹配处在“岗位准备决策”上，候选人需要在面试中讲清楚为什么选择某个故事。如果只给出一个 Embedding 相似度，用户很难知道是技术栈命中、职责命中还是背景词偶然相似。

当前规则虽然覆盖有限，但每个加分项都有对应字段：JD 出现越多，说明关注度越高；技术栈和职责命中，说明项目更适合承担证明责任。以后可以引入语义模型作为候选排序器，但仍应保留字段证据和用户确认。

## 与追问卡、Agent 的连接

排序结果不会直接创建计划。页面把代表性卡片 ID 传给 Agent：

```text
JD focus high
  -> 项目匹配 score 高
  -> 选择关键设计/效果验证卡
  -> Agent read_question_card
  -> draft project_followup plan
  -> 用户确认
```

一般技能使用“关键设计”卡；评测和性能优化使用“效果验证”卡。分数只决定准备顺序，卡片仍然覆盖项目背景、职责、设计、验证和取舍五个维度。

## 可用于面试的追问

### 为什么技术栈字段权重最高？

因为它是最直接的技术证据；但分数不会只看技术栈，职责和关键工作也参与计算，避免“简历罗列技术名词”就获得完整匹配。

### 为什么 high 不是模型预测的录用概率？

high 只表示该技能在当前 JD 的关注优先级，来自可观察的出现频次排序。它不判断候选人的能力，也不替面试官做录用决策。

### 如果两个项目得分相同怎么办？

当前使用项目名作为稳定的第二排序键，保证同一输入结果可复现。后续可以让用户手动确认首选项目，或加入真实结果/职责深度等结构化信号。

### 为什么不直接让匹配结果修改 Agent 计划？

匹配是只读建议，计划是持久化写操作。用户需要先进入 Agent，Agent 再读取卡片并生成 draft，确认后才 active；这保持了第 29 阶段的受控行动边界。

## 验证结果

- 项目匹配返回 `priority` 和 `score`；
- 分数考虑 JD 出现次数、岗位优先级和命中字段；
- 前端按后端排序展示优先级和匹配分数；
- 既有卡片/Agent/专项训练链路没有改变；
- 暂存工程后端 `45 passed`，Python compileall、前端 typecheck 和生产构建通过。

## 当前限制与下一步

- 技能词表仍是人工维护，优先级只使用出现顺序，不理解句法否定或职责语义；
- 分数不是概率，也没有置信区间、用户反馈校准或语义重排；
- 下一步可以增加用户确认的项目首选项和更细的岗位 focus 解析，再统一进行干净环境复现；真实资料联调、外部部署和 GitHub 推送仍需单独确认。
