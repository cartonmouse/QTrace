# 阶段 17：Agent 学习计划的对话绑定与历史恢复

## 发现的问题

真实账号联调时，学习计划可以成功生成、确认和完成；但刷新 Agent 页面后，历史对话虽然能恢复，计划操作卡却不会自动出现。原因是前端只把 `created_plan` 当作当前请求的临时响应，没有在打开历史对话时重新读取计划。

这会把一个已经持久化的业务状态误表现成一次性消息，用户无法从历史页面继续完成计划项。

## 设计修复

学习计划新增可空的 `conversation_id`：

```text
Agent 对话
    |
    +-- 用户请求生成计划
            |
            +-- learning_plans.conversation_id
```

创建计划时，`run_personal_agent()` 把当前对话 ID 传给受控写工具，Store 在同一用户范围内保存关联关系。打开历史对话时，前端同时读取该用户的计划列表，优先按 `conversation_id` 找到计划并恢复操作卡。

对于阶段 16 已经存在的旧计划，`conversation_id` 为空；前端临时使用“计划来源消息是否出现在该对话中”做兼容匹配。新建计划都会使用显式对话 ID，不再依赖文本猜测。

## 数据迁移

旧 SQLite 数据库启动时执行 `_migrate_learning_plans()`：

1. 检查 `learning_plans` 是否已有 `conversation_id` 列；
2. 没有则通过 `ALTER TABLE ... ADD COLUMN` 增加可空列；
3. 创建按用户、对话和更新时间排序的索引；
4. 不删除、不覆盖旧计划。

可空设计是为了让历史计划安全升级，不需要伪造它们的来源对话。

## 验证

- Agent 创建计划的返回值包含 `conversation_id`；
- 计划列表接口返回同一关联字段；
- 用户隔离测试继续覆盖计划确认和查询；
- 前端 TypeScript 类型检查和生产构建通过；
- 真实账号联调已观察到：计划生成、确认、第一项完成均成功；正式目录重启并刷新页面后，历史计划卡恢复，第一项仍保持完成状态。

## 面试追问卡

### 为什么不只按 source_message 匹配？

因为用户可能在不同对话中重复发送同一句话，文本不是稳定的业务主键。新计划显式保存 `conversation_id`，查询关系更准确；旧数据才使用 source message 兼容恢复。

### 为什么 conversation_id 允许为空？

迁移时不能为历史数据猜测来源对话。可空字段允许旧数据继续查询，同时让新数据逐步拥有明确关联；这是兼容升级比强制回填更安全的取舍。

### 计划和对话为什么仍然分表？

对话保存消息轨迹，计划保存可执行状态。分表避免把状态字段塞进自然语言消息 JSON，也让计划确认、完成、查询和用户隔离可以独立测试。
