# 阶段 55：AI Agent 面试追问防守包

## 使用方法

这份材料服务于“能把项目讲清楚，并能承受追问”，不是把没有实现的能力包装成亮点。回答时遵循三句话结构：

1. 先说系统解决的问题和自己的设计边界；
2. 再说一条真实代码链路、状态或测试证据；
3. 最后主动说当前限制和下一步。

项目定位是“独立重建一个 TechSpar 风格的个性化面试训练系统”，不是声称自己开发了上游仓库。当前工程名为问迹 QTrace，核心价值是把结构化简历、训练记录、画像、知识图谱、SM-2 复习项和 Personal Agent 连接起来。

## 1. 90 秒项目介绍

“我做的是问迹 QTrace，一个面向求职训练的个人 Agent 系统。我希望解决的问题是：用户有简历、知识材料和很多次训练记录，但下一次该练什么、为什么练、练完如何留下长期反馈，通常是断开的。

我把系统拆成四层。第一层是事实资料，包括结构化简历、个人文档、领域题库和训练历史；第二层是确定性读模型，包括项目追问卡、知识图谱和 SM-2 到期复习项；第三层是 Personal Agent，它通过规划、只读工具和回答两步读取用户上下文，提出学习计划；第四层是受控写入，学习计划先保存为 draft，用户确认后才进入 active，训练和复盘再更新后续事实。

我没有让模型直接改数据库。后端负责用户隔离、工具白名单、参数校验、失败降级和状态机。当前用 StubProvider 可以完整离线运行，也有 OpenAI-compatible 的 LLM/Embedding 适配边界。我的验证证据包括后端自动化回归、前端构建、本地运行态检查和合成主链彩排。真实长音频、WebSocket 实时辅助、全新目录公开复现和部署，我会明确标成未完成边界。”

## 2. 架构与数据边界

### Q：为什么选择 React + FastAPI + SQLite？

A：这是一个学习型独立重建项目，我优先选择能看清调用链、容易本地运行和容易测试的技术栈。React/Vite 负责多页面交互，FastAPI 负责鉴权、输入校验和编排，SQLite 负责本地状态持久化。它不是为了宣称生产级分布式架构，而是先把领域状态和边界做实。未来如果数据规模或并发要求提高，可以替换存储层和异步任务层，但 Agent 的工具协议和领域服务接口不应被具体数据库绑死。

### Q：一次“生成学习计划”请求具体经过哪些步骤？

A：前端把消息、对话 ID、可选主题/问题卡 ID 发到 Agent 路由。后端先校验当前用户和上下文来源，再调用规划器得到受控工具名；后端逐个执行只读工具，把结果和失败 trace 组装成工具上下文；如果规划中包含写计划，必须先通过画像、到期复习、近期训练等依赖门禁；最后调用回答阶段，保存用户消息、Agent 消息和可能的 draft。返回给前端的是回答、工具 trace、对话和计划卡，而不是一段无法追溯的纯文本。

### Q：为什么前端不能直接调用模型？

A：模型配置中可能有敏感的 API Key，而且用户隔离、工具白名单、计划状态和数据库事务边界不能交给浏览器。前端只负责展示和发起意图，后端负责把模型输出解析成受控结构，再决定哪些工具能执行、哪些字段能写入。

### Q：为什么没有把图谱单独做成一套事实数据库？

A：当前图谱是 read model。题库、主题、画像、复习项和训练 session 才是事实源；`backend/graph.py` 根据当前用户和主题即时构建节点与边。这样打开图谱不会意外写画像或 SM-2，也不会产生第二份容易过期的题库事实。它牺牲了一些预计算性能，换来可解释、可复现和容易测试。

## 3. Agent 与工具调用

### Q：你的 Agent 和普通工作流有什么区别？

A：固定工作流可以把每一步都写死；Agent 的规划器可以根据用户目标选择一组受控工具并组织回答上下文。但我没有把“模型能规划”理解成“模型拥有系统权限”。真正的执行仍是后端白名单、用户作用域、参数验证和状态机。可以把它描述为“LLM 负责选择与组织，后端负责事实读取和业务写入”。

### Q：为什么规划和回答要分两步？

A：规划阶段的输出是意图和工具调用列表，后端可以先做白名单归一化、否定意图保护和上下文依赖检查；工具执行结果带有状态和来源，再交给回答阶段。这样模型不能在一段自然语言里偷偷混入未经执行的事实，也方便把规划失败、工具失败和回答失败分别观测。代价是多一次模型调用和更高延迟，所以当前 StubProvider 和真实 Provider 都复用同一套边界。

### Q：工具失败时为什么有的继续、有的不继续？

A：读取工具通常可以 best-effort。例如画像读取失败，但到期复习和近期训练仍成功时，回答可以基于部分上下文继续，并明确缺失信息不能当成零值。写工具不一样，因为它会产生持久化状态。`create_learning_plan` 要求画像、复习队列和近期训练读取成功；任一前置失败时只记录 `write_blocked_by_context`/`skipped`，不创建 draft。

### Q：如果模型输出了不存在的工具名怎么办？

A：先做工具名白名单归一化，未知工具不会执行；同时把规划结果和执行 trace 分开保存。生产实现还需要补充更细的结构化输出校验和供应商差异测试，但当前不会把模型字符串直接当作函数名或 SQL 执行。

### Q：为什么学习计划必须用户确认？

A：计划是跨请求持续存在的业务状态，不应由一次模型回答隐式产生。draft/confirm 把“模型建议”与“用户同意执行”分开，也使幂等、历史恢复、计划项完成和训练审计有明确状态。Agent 可以主动提出下一步，但用户拥有最终写入权。

## 4. 记忆、RAG、图谱与 SM-2

### Q：结构化简历、个人文档、画像和图谱分别是什么？

A：结构化简历是用户主动维护的核心身份事实，字段稳定，适合渲染成面试上下文；个人文档是更详细的项目材料，支持分块、Embedding、版本和 citation；画像是训练复盘沉淀的强项、薄弱点和行为信号；图谱是把题库、画像、复习事实组织起来的只读视图。它们不是四份互相复制的“记忆”，而是不同来源、粒度和生命周期的数据。

### Q：这个项目哪里用了 RAG？

A：个人文档链路使用了文本规范化、分块、Embedding、用户隔离检索和 citation。当前默认有本地确定性 Embedding baseline，也有可替换的 OpenAI-compatible Embedding Provider；切换外部模型后需要用户显式重建索引。Agent 的 `search_personal_documents` 是只读工具，引用告诉回答证据来自哪份文档哪个版本/分块，但 citation 不等于系统已经验证事实。

### Q：图谱的 related 边是不是 Embedding 相似度？

A：不是。当前图谱为了可解释和可复现，使用题目 token 重叠并对中文补充二元字符片段；它不是向量语义相似度，也不是能力评分。Embedding 负责个人文档证据召回，图谱负责题库结构和复习关系，两条链路分开。

### Q：画像和 SM-2 如何共同影响出题？

A：画像回答“长期哪些方面弱、哪些行为值得关注”，SM-2 回答“某个复习项什么时候再次出现”。训练出题会合并画像、主题、近期训练、用户显式 focus 和到期复习项；开始一道题不会直接把它标记为掌握，复盘才是写回训练结果和调整复习状态的边界。

### Q：为什么不让模型直接生成用户画像？

A：画像属于长期事实，直接由模型自由改写会带来幻觉和不可审计变化。当前采用结构化复盘结果和后端确定性写回边界；模型可以提供结构化建议，但最终要经过解析、校验和业务规则。现阶段也没有宣称画像自动化已经覆盖所有真实训练场景。

## 5. 稳定性、安全与一致性

### Q：LLM 超时、429 或返回非 JSON 怎么办？

A：Provider 层负责把供应商错误归一化并做有界重试，鉴权错误不盲目重试；Agent 层再把规划失败和回答失败映射成稳定的 API 错误码。非 JSON 规划不能直接进入工具执行，解析失败应当回到可观察的失败状态。当前项目已覆盖合成失败边界，但没有把外部供应商的所有兼容性都说成已验证。

### Q：回答失败时为什么有时回滚对话，有时保留草稿？

A：模型调用不是 SQLite 事务。若新建对话没有消息、没有计划，失败补偿可以按用户和状态条件清理空壳；如果计划 draft 已经产生，就不能因为后续回答失败删除有效业务结果，而是返回 `preserved_draft` 和已验证的 conversation ID，让用户查看、确认或重试。前端还要移除未持久化的乐观消息并恢复输入。

### Q：怎样防止跨用户读取？

A：所有 Store 查询和写入显式带 `user_id`；对话、计划、文档、简历版本、图谱主题和训练 session 都在路由或服务层重新校验归属。前端传来的 ID 只是候选，不是权限证明。API Key 只用于本地 Provider 配置，不由设置查询接口返回给前端；公开仓库和测试使用合成配置。

### Q：有没有解决 Prompt Injection？

A：不能过度声称已经解决。当前主要防护是工具白名单、后端权限边界、个人文档只作为证据上下文、写操作确认和错误脱敏；还需要在真实对抗数据上补充文档指令注入、工具参数污染和模型越权的专项测试。因此面试中应说“降低了工具越权风险”，不要说“完全防住了 Prompt Injection”。

## 6. 评估与工程取舍

### Q：如何证明 Agent 真的有用？

A：当前有三层证据但还不是完整效果实验。第一层是契约测试，验证工具调用、用户隔离、draft/confirm 和失败降级；第二层是合成主链彩排，验证状态可以从简历/图谱走到计划完成；第三层是图谱候选的只读行为评估，统计开始/完成、有效复盘分数和重复训练比例。它们证明系统行为和可观测性，不等于已经证明学习收益或面试通过率提升。下一步需要固定任务集、离线指标和用户实验。

### Q：为什么不直接上多 Agent、WebSocket 和真实长音频？

A：这些能力会扩大状态、并发、外部服务和调试复杂度。当前先把文本训练、Personal Agent、检索、画像和 SM-2 主链做成可运行、可解释和可测试的垂直切片；真实长音频、说话人分离、时间戳、完整多 Agent 并行和 WebSocket 实时辅助明确留在交付范围外。这个取舍让项目更容易在面试中讲清边界。

### Q：SQLite 能支撑生产吗？

A：当前目标是本地学习和独立复现，SQLite 足以展示数据模型、用户隔离和状态迁移。生产场景还要评估并发写、连接池、备份、异步任务和 PostgreSQL 等替代方案。我的回答重点是“我把存储边界抽象出来，并知道 SQLite 的限制”，而不是声称它已经经过生产压测。

### Q：你做了哪些测试？

A：后端用 pytest/TestClient 覆盖认证、训练状态机、简历版本、文档检索、图谱、SM-2、Agent 工具、计划确认、失败补偿和跨用户边界；脚本层有 repository/reproduction/runtime/frontend/final-delivery/synthetic-demo 等只读检查；前端做 TypeScript typecheck 和 Vite build。当前没有独立浏览器自动化，所以人工彩排仍是单独门禁。

## 7. 高频追问速答

### “你说 Agent 能个性化，个性化依据是什么？”

答：不是一句 prompt 里凭空说“根据用户画像”，而是后端按当前用户读取结构化简历/文档、画像强弱点、主题、近期训练和 SM-2 到期项，再把用户当前显式目标作为 focus 传入。计划和训练会保留来源，便于追溯。当前个性化更多是上下文组合和确定性规则，不宣称已经有复杂推荐模型。

### “为什么模型不直接把计划写进数据库？”

答：因为模型输出不等于授权。后端需要验证用户、工具、前置上下文和字段，再用 draft/confirm 让用户确认；这样可以审计、恢复、幂等，也避免模型幻觉直接产生长期业务状态。

### “检索不到证据怎么办？”

答：返回空证据并明确需要补充准备材料，不让模型编造引用。回答可以基于成功读取的其他上下文继续，但必须说明文档证据缺失。检索失败是可观察的工具状态，不是“没有资料”的事实。

### “为什么不把所有内容都塞进 prompt？”

答：全部拼接会带来 token、延迟、隐私和过期内容混入问题。结构化字段用于稳定上下文，个人文档先分块检索，图谱和复习项只返回当前相关 read model，Agent 工具把事实读取和回答过程分开。

### “你的最大技术难点是什么？”

答：不是把页面做出来，而是处理模型调用和业务状态之间的不一致：规划可能成功、工具可能部分失败、写计划可能已经产生 draft、回答又可能失败。我的解决方式是稳定错误协议、工具 trace、写工具依赖门禁、空对话条件补偿、保留 draft 和前端显式恢复。

### “如果让你继续做，你先做什么？”

答：先完成合成账号下的浏览器人工彩排，记录页面状态和可用性问题；然后做全新目录的可复现安装和版本冻结；再根据真实合成任务集补充 Agent 质量评估，最后才确认真实资料联调、公开推送和部署。这样每一步都有独立门禁，不把环境问题和模型质量问题混在一起。

## 8. 不足与诚实边界

面试中主动列出以下限制反而更可信：

- 当前验证以本地 StubProvider、合成账号和本地数据库为主；
- 真实 LLM/Embedding 只在显式配置和合成输入边界下联调，供应商兼容性不等于全部验证；
- 尚未完成独立浏览器自动化、全新目录正式复现和外部部署；
- 真实长音频、说话人分离、时间戳对齐、多 Agent 并行 Copilot、WebSocket 实时辅助和简历 PDF 排版不在当前交付范围；
- 图谱反馈是描述性行为统计，不是 A/B 实验，也不能证明学习因果收益；
- SQLite 和同步调用适合本地学习工程，尚未做生产并发和成本压测。

不要说：“系统已经完全理解简历”“图谱就是向量数据库”“Agent 可以自动替用户执行所有操作”“已经支持 WebSocket 实时面试”“真实效果已经证明”。

## 9. 彩排时的证据顺序

1. 先运行 `python scripts/synthetic_demo_smoke.py`，证明后端状态主链；
2. 再展示 `python -m pytest -q`、前端 build 和 `python scripts/final_delivery_preflight.py`；
3. 用户使用合成账号在浏览器中按“设置 -> 简历编辑器 -> 追问卡 -> 知识图谱 -> Agent draft -> confirm -> 训练/完成”操作；
4. 最后展示一个 fake provider 失败用例，说明输入恢复、保留草稿和错误脱敏；
5. 以“已完成证据/未完成边界/下一步门禁”收尾，而不是只展示漂亮页面。
