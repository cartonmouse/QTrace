# 阶段 8：录音转写复盘

## 目标

参考项目把“面试录音”和“复盘结果”连在一起。本阶段先实现一条可验证的文本优先链路：用户粘贴已经得到的面试转写，系统解析说话人、估计回答质量、生成复盘，并把结果写入会话历史和能力画像。

这样做的重点不是假装已经完成音频识别，而是先把领域模型和复盘主链固定下来。ASR 只保留为可替换边界，不作为本项目必须交付的音频能力。

## 用户流程

```text
录音转写
  -> 选择双人/个人模式
  -> 粘贴带说话人标签的文本
  -> 解析为 assistant/user 消息
  -> 生成回答评分、优点、薄弱点和行动项
  -> 保存 recording session
  -> 写回全局画像和今日复习队列
```

双人转写建议使用如下格式：

```text
面试官：请介绍一个你负责的 RAG 项目。
你：我负责了检索链路，先做文档切分和向量化，再通过召回和重排提升命中率。
面试官：你如何验证效果？
你：使用离线问题集评测 Recall@K，并结合线上反馈调整 chunk size。
```

个人模式适合只有候选人回答的笔记或转写。系统不会根据段落数量臆造面试官问题，而是把全文视为一个回答片段，避免错误的对话边界进入复盘。

## 后端模块

### `backend/recording.py`

- `parse_transcript`：识别 `面试官`、`你`、`候选人`、`interviewer`、`candidate` 等标签；连续的无标签行并入上一条消息。
- `analyze_transcript`：生成统一的 `review` 结构，包含 `average_score`、`scores`、`strengths`、`weak_points`、`action_items`、`transcript_meta` 和 `segments`。
- 当前评分是可解释的启发式规则：回答长度、数字/百分比、结果/指标/验证/复盘等事实信号，以及“因为—所以—首先—然后—最后”等结构信号会影响分数。

### 会话持久化

录音复盘使用普通 `sessions` 表，因此历史、详情和画像接口可以复用已有协议；同时保存：

- `recording_mode`：`dual` 或 `solo`；
- `source_transcript`：本轮原始文本；
- `recording_meta_json`：字符数、消息数、问题数、回答数、估计时长和是否检测到说话人标签。

在真实项目中，原始转写属于敏感数据，需要增加保留期限、脱敏、访问审计和用户主动删除。当前学习工程只使用本地合成文本，不上传外部服务。

## 为什么先做文本优先

录音复盘可以拆成两个边界问题：

1. 外部来源如何得到转写文本；
2. 转写后的对话分析和复盘。

本阶段完成第 2 层，并规定稳定的转写输入契约。这样可以单独测试复盘逻辑，也能在没有音频识别服务时让用户手动粘贴转写继续使用。ASR 只保留如下替换点，不扩展真实音频处理：

```text
TranscriptSource -> ASRProvider -> TranscriptDocument -> RecordingAnalyzer -> Review
```

其中 `ASRProvider` 可以未来接入兼容 HTTP 服务，但当前使用人工粘贴和文本 mock；`RecordingAnalyzer` 可以从规则版替换为真实 LLM，但输出仍要经过结构化校验。

## 面试追问卡

### 为什么不直接在前端录音并上传？

因为录音涉及浏览器权限、文件大小、编码、网络超时和敏感数据保留。先定义 `TranscriptDocument`，可以把 ASR、上传和复盘解耦，任何一层失败都能明确降级。

### 为什么不能简单按换行切成问答？

换行不等于说话人边界。错误边界会让系统把面试官问题当成候选人回答，进而污染评分和画像。因此双人模式只有识别到明确标签才切换角色，未标注文本则保守合并。

### 现在的评分是不是 LLM 评分？

不是。本阶段是本地可解释的启发式评分，目的是跑通数据结构和复盘闭环。真实 LLM 接入应放在 `RecordingAnalyzer` 接口后面，并校验结构化 JSON；规则版作为离线测试和模型不可用时的 fallback。

### 为什么录音复盘可以复用已有画像？

复盘的输出已经统一为 `Review`，画像只关心得分、薄弱点和行动项，不必关心结果来自实时面试还是录音复盘。会话的 `mode` 和快照仍然保留来源，便于历史解释。
