# Stage26：结构化简历编辑器与面试上下文

## 目标

之前的简历入口有两个问题：PDF 只能整体上传，文本摘要也只是一个大文本框。这样的数据可以启动面试，但无法稳定回答“哪个项目是你的职责”“这个项目用了什么技术”“应该把哪条经历传给 Agent”等问题。

本阶段实现一个最小但完整的结构化简历编辑器：

- 用姓名、目标方向、个人概述、技能和项目经历表达简历核心信息；
- 项目经历包含职责、概述、技术栈和可独立追问的关键工作/结果；
- 保存后生成稳定的“面试上下文”文本；
- 每次正文变化保存为一个新版本，旧版本可以查看和重新载入；
- 简历面试、JD Prep、Copilot 和 Personal Agent 在没有 PDF 文本时可以读取结构化简历。

这是一个字段化的学习版本，不试图一次复制参考项目完整的多页简历编辑器、拖拽排版和导出系统。

## 领域模型

### Structured resume profile

结构化简历是当前用户的一份长期资料，当前版本包含：

```text
StructuredResume
├── name
├── headline
├── email / location
├── summary
├── skills[]
└── projects[]
    ├── name
    ├── role
    ├── description
    ├── technologies[]
    └── highlights[]
```

`projects` 是本阶段的重点。面试官追问项目时，系统不仅能拿到项目名称，还能拿到“我负责什么、做了什么设计、用了哪些技术、如何验证”的证据。

### Interview context

结构化字段不直接传给 InterviewEngine 或 LLM，而是先由确定性渲染器转换为稳定文本：

```text
姓名：QTrace Learner
目标方向：AI 应用开发工程师
个人概述：负责 AI 应用和个人 Agent 的工程化落地
技能：Python、FastAPI、RAG、Agent
项目经历：
- 问迹 QTrace（独立负责后端与 Agent 编排）
  项目概述：...
  技术栈：FastAPI、SQLite、React
  关键工作：设计两步 Agent：规划 -> 工具执行 -> 回答
```

渲染器只负责把字段组织成模型和状态机已经能理解的文本，不负责生成事实、不调用 LLM，也不做语义推断。因此面试中可以清楚地区分：

- 结构化简历负责保存事实；
- Context Renderer 负责格式转换；
- InterviewEngine、JD 分析器和 Agent 负责消费上下文。

## 版本存储

当前状态和历史快照分开保存：

```text
resume_profiles
  -> 当前 profile_json、context_text、version、profile_hash

resume_profile_versions
  -> 每个版本的 profile_json、context_text、created_at
```

同一用户只有一份当前结构化简历。第一次保存生成 `v1`；正文指纹发生变化时生成 `v2`、`v3`。指纹使用规范化后的结构化 JSON 计算 SHA-256：

- 同样的字段再次保存返回 `unchanged=true`，不增长版本；
- 标题、技能、项目职责等事实变化会产生新版本；
- 版本保存使用 SQLite `BEGIN IMMEDIATE`，快照和当前指针不会只写一半。

旧数据库启动时只创建新表，不改变 PDF 简历文件和既有训练会话；结构化简历是独立的渐进式能力。

## 接口

```text
GET  /api/resume/editor
PUT  /api/resume/editor
GET  /api/resume/editor/versions
GET  /api/resume/editor/versions/{version}
```

默认 GET 在用户尚未保存时返回空 profile 和 `version=0`，让前端可以直接展示编辑器。版本列表只返回元数据；打开某个版本时才返回完整字段和渲染后的上下文。

所有接口都依赖 JWT，并在 Store 查询时显式带 `user_id`。用户 A 即使知道用户 B 的版本号，也只能得到空列表或 404，不会获得 B 的项目内容。

## 上下文消费优先级

为了兼容已有 PDF 链路，同时支持新编辑器，各业务入口使用如下顺序：

```text
用户在请求中显式提交 resume_text
  -> 已上传 PDF 的抽取文本
  -> 结构化简历渲染文本
  -> 空文本（由上层决定是否允许继续）
```

Personal Agent 的 `read_resume` 工具也遵循同一顺序，并在工具结果中标记 `source=pdf` 或 `source=structured-editor`。这样不用改 Agent 工具名和回答协议，就能把新编辑器接入已有个人画像系统。

## 前端闭环

`/resume-editor` 页面分成三部分：

1. 字段编辑区：维护个人信息、概述、技能和项目证据；
2. 面试上下文预览：实时显示确定性渲染结果；
3. 历史版本区：按新到旧展示版本，载入历史版本后再次保存会创建新版本。

页面明确显示当前版本和“保存为新版本”，避免用户把版本快照误解成覆盖式草稿。PDF 上传仍然保留在首页，两个入口可以并行使用。

## 面试追问卡

### 为什么要做结构化简历，而不是继续使用一段长文本？

长文本适合快速导入，但不适合可靠地按字段取事实。结构化字段让系统知道项目名称、职责、技术栈和关键结果分别在哪里，Agent 可以基于这些字段生成更具体的追问，而不是每次都重新猜测文本结构。

### 为什么不让 LLM 直接从简历生成 JSON？

当前目标是先建立可解释、可编辑、可验证的数据边界。用户填写的字段是真实来源，确定性渲染不会引入模型幻觉；将来可以让 LLM 辅助抽取，但抽取结果仍应经过用户确认后再保存。

### 结构化简历和个人文档有什么区别？

结构化简历是有固定字段和当前版本的核心身份资料，主要服务于面试上下文；个人文档是用户主动保存的项目说明、技术方案和复盘笔记，主要服务于 RAG 检索。简历回答“我有哪些经历”，个人文档提供“某个经历的详细证据”。

### PDF 和结构化编辑器同时存在时使用哪个？

用户显式传入的文本优先，其次是已上传 PDF，最后才是结构化简历。这样保持已有 PDF 用户的行为不变，同时让没有 PDF 的用户也能用编辑器开始训练。未来可以增加“从 PDF 抽取到字段”的显式确认流程，而不是静默覆盖用户内容。

### 为什么简历版本需要单独建表，不能复用个人文档版本表？

两者的领域身份不同：个人文档按正文精确去重并按文档 ID管理多份资料，结构化简历是每个用户唯一的一份字段资料。分表能让约束、查询和面试语义清楚，避免把“简历字段修改”误当成“新增一份个人文档”。

### Agent 如何读取结构化简历？

Agent 仍然调用受控的 `read_resume` 工具。工具先尝试读取 PDF，PDF 不存在或没有文本时再读取结构化简历的 `context_text`，并返回来源类型、版本和文本长度；Agent 不能直接访问 SQLite。

## 验证结果

- 未保存时 GET 编辑器返回空 profile 和 `version=0`；
- 新 profile 保存为 `v1`，内容指纹不变时幂等返回；
- 修改个人概述生成 `v2`，历史列表返回 `[2, 1]`；
- `v1` 和 `v2` 的字段可以分别读取；
- 没有 PDF 时，面试启动会把结构化渲染文本保存到 session 的 `resume_text`；
- Personal Agent 的 `read_resume` 可以读取结构化简历，并标记来源；
- 暂存工程完整后端测试 `43 passed`；Python compileall、前端 typecheck 和生产构建通过。

## 当前限制与下一步

- 当前只覆盖核心项目简历字段，尚未加入教育、工作经历、时间轴拖拽、模板排版和 PDF 导出；
- 历史版本目前支持查看和重新载入，没有 diff、回滚按钮和引用点击跳转；
- 目前没有 PDF -> 结构化字段的 LLM/规则抽取向导，避免未经确认地改变用户事实；
- 下一步可以补充简历字段校验、项目追问卡和结构化字段到 Agent 计划的证据映射；真实资料联调、外部部署和 GitHub 推送仍需单独确认。
