# 阶段 49：Personal Agent 可恢复交互

## 目标

阶段 47/48 已经让后端知道失败后哪些状态被回滚、哪些计划草稿被保留，以及工具是否发生降级。本阶段把这些状态变成用户可以直接操作的前端闭环：失败后可以显式重试；如果回答失败但计划草稿已经存在，可以准确加载这份草稿再确认，而不是重复发送请求。

本阶段只使用本地代码、合成测试和构建验证，没有调用真实 LLM，没有读取或上传真实简历/个人文档，没有部署、删除文件或提交推送 GitHub。

## 实现

### 统一发送入口

Agent 表单和“重新发送”按钮都调用 `submitMessage`：

- 发送前清理上一条错误状态，并添加乐观用户消息；
- 成功时保存对话、回答、规划和工具轨迹；
- 失败时移除未持久化的乐观消息，把原文恢复到输入框，并保存 `retryMessage`；
- 重试仍由用户点击触发，不自动循环，避免模型服务异常时产生请求风暴或重复写入。

### 失败操作区

错误区域现在使用 `role=alert`，根据状态提供不同操作：

- 普通规划/回答失败：显示“重新发送”；
- `state=preserved_draft`：同时显示“加载保留草稿”；
- 没有保留草稿时，不显示误导性的加载按钮。

### 草稿精确恢复

阶段 47 的 `preserved_draft` 错误只额外返回后端确认的 `conversation_id`。前端加载计划时按该 ID 过滤 `status=draft`，避免用户有多条历史计划时误载入其他草稿。加载失败仍显示错误，不把按钮点击当作成功。

## 面试讲解要点

### 为什么重试不自动进行？

重试可能再次触发模型费用、延迟和受控写工具。当前系统先恢复输入并把重试权交给用户；后续若要自动重试，应在请求幂等键、退避、次数上限和写工具幂等都明确后再做。

### 为什么前端要恢复输入文本？

失败请求没有产生持久化回答，页面不应保留一条看似成功的用户消息；恢复文本让用户可以修改上下文或直接重试，同时保持对话历史和页面状态一致。

### 为什么不能只加载最新 draft？

用户可能同时有多条 Agent 计划，最新创建时间不等于当前失败请求产生的计划。后端只在保留草稿的错误状态中返回已验证的对话 ID，前端再按用户作用域和对话 ID匹配。
