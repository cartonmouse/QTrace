# 阶段 4：主题知识库与专项训练

## 目标

复现参考项目的专项训练主链：

```text
用户创建/选择训练领域
  -> 维护核心知识 Markdown 和高频题库
  -> 启动 topic_drill 会话
  -> 本地检索相关知识片段
  -> 与高频问题一起组装成 Provider 上下文
  -> 复用面试状态机出题、追问和复盘
```

专项训练和简历面试的区别是上下文来源不同：简历面试优先使用候选人自身经历，专项训练优先使用某个技术领域的知识和题库；回答、阶段推进、复盘和历史记录仍然复用同一条主链。

## 数据布局

```text
<数据目录>/users/<user_id>/
├── topics.json
├── knowledge/<topic>/README.md
└── high_freq/<topic>.md
```

新用户第一次访问 `/api/topics` 时会得到 Python、RAG、Agent 三个适合当前项目的演示领域。用户创建的领域不会覆盖预置领域；删除领域时只操作当前用户自己的目录。

## 检索实现

当前版本使用“段落切分 + 关键词重叠评分”：

1. Markdown 文件按空行切成段落，再以约 1,000 字符为上限合并，并保留少量重叠。
2. 用中文单字和英文技术词生成 token 集合。
3. 根据训练领域名称和高频问题计算 chunk 与查询的重叠分数。
4. 取前若干片段，控制上下文字符预算。

领域内容较少时直接返回完整文档，避免小语料被检索误删；内容较大时才选择 top-k。这与向量检索的调用边界保持一致，后续可以把 `retrieve_topic_context` 替换成 Embedding + 向量库，而不改动路由和面试状态机。

## 关键代码

| 文件 | 责任 |
| --- | --- |
| `backend/knowledge.py` | 领域、文件、题库 CRUD；切分和本地关键词检索 |
| `backend/main.py` | 知识库 API；启动 `topic_drill` 时组装上下文 |
| `backend/interview.py` | 复用统一阶段状态机，把 topic context 传给 Provider |
| `backend/provider.py` | StubProvider 使用题库出题；OpenAI Provider 将知识上下文放入 prompt |
| `backend/store.py` | 保存会话 mode、topic、知识上下文和题库快照，支持历史复现 |
| `frontend/src/App.tsx` | 专项训练选择页、知识库编辑器和题库编辑器 |

## 为什么保存题库快照

启动训练时把当时的知识上下文和题库写入 session，而不是每次回答都重新读取文件。这样一轮训练过程中内容稳定，历史会话也能解释“当时模型为什么这样出题”。知识库更新只影响下一轮训练。

## 面试追问卡

### 1. 为什么不直接用随机题库？

随机题库只能保证覆盖题目，不能保证问题和知识重点、上一轮回答相连。这里把题库作为高频问题参考，把核心知识作为评分和追问上下文，Provider 才能动态生成问题。

### 2. 为什么当前不用向量数据库？

当前用户数据规模小，本地关键词检索更容易运行、调试和解释。代码把检索封装在 `retrieve_topic_context`，未来可以替换为向量检索并单独比较召回率、延迟和成本。

### 3. 为什么小文档直接返回全文？

小文档中每一段通常都属于同一个领域，强行 top-k 可能把重要的边界条件漏掉。只有超过上下文预算时才需要检索压缩。

### 4. 如何防止用户输入的知识文件穿越目录？

领域 key 和文件名都拒绝路径分隔符；服务端重新解析并校验最终路径必须位于当前用户的知识根目录下；所有路由先通过 token 得到 user_id。

### 5. 专项训练和 RAG 是一回事吗？

不是。专项训练是产品场景，知识检索是其中的上下文准备步骤。当前版本是轻量关键词检索，还没有 Embedding、向量索引、混合检索和重排，因此不能把它描述成完整生产 RAG。
